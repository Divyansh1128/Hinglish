## B2 — manifest verification

**Trainer boundary.** The tokenizer, config and generation file hashes (`HUB_FILES`) and the chat-template record (`CHAT_TEMPLATE`) now live in `t4_smoke/train_phase2.py`. The manifest builder reads them from there, so there is one source.

- `verify_implementation` refuses a manifest whose `model.hub_files`, `model.chat_template`, tokenizer revision or `baseline_dev` identities differ from the trainer's own values.
- Inside every attempt, at stage `hub`, `verify_hub_files` re-downloads the 7 pinned files with `hf_hub_download` and compares their bytes.
- At stage `tokenizer`, `verify_chat_template` compares the loaded template's digest and UTF-8 SHA-256 with the manifest.
- A mismatch is a protocol failure, so the study halts. A download error stays a network/Hub infrastructure failure.
- This is in the executable (`tp.main`), so it also holds when the trainer is run directly, not through the notebook.

**Freeze.** `freeze_manifest` now calls `verify_manifest_current`. That function does three things:
1. Rechecks the hashed files as before.
2. Loads `phase2/build_implementation_manifest.py` from `root` and runs `build()`.
3. Requires the required file set and every non-file entry (dependency pins, recipe, settings and so on) to be equal. A refusal names the differing paths, for example `dependencies.evaluation.torch`.

## B3 — baseline evidence (training side)

**`verify_baseline(baseline_dir, manifest)`.** The second argument is now the manifest file, not its SHA. A bare SHA is refused, because a hash alone cannot validate an archive. The function checks the record as before, then validates the ZIP itself:

- **Complete export:** every member of the engine export (`BASELINE_MEMBERS`) is present, and `checksums.sha256` lists exactly the members, each with the right hash.
- **Engine identity:** the `source/*.py` snapshot equals the manifest's engine group. The recomputed `code_sha256` equals the run manifest, the record and the manifest.
- **Configuration:** the config digest is recomputed and must equal the run manifest and the record. `experiment_config.json` must be the registered DEV configuration (`generation_config.engine_config_sha256.dev`): decoding, prompt, unchanged model, pinned revisions.
- **Frozen DEV:** the dataset and split digests must equal `DEV_DATASET_SHA256` / `DEV_SPLIT_SHA256` and the manifest's `baseline_dev` entry. `dataset_snapshot.jsonl` must match `dataset.json`, and the evaluation order must be the engine-seed shuffle of the 120 renderings.
- **Execution and environment:** checked by `execution_problems`; the field names are listed in the section below.
- **Generations:** exactly 120 resolved generations (`generation_problems`). Every journal record's digest must recompute and belong to this run and config. Attempt numbering, the retry limit and the never-retry-a-generation rule must hold. `errors.jsonl` and the attempt count must be consistent.

**Authenticated at creation.** `bind_implementation` now runs `verify_running_implementation` before recording anything. It checks:
- Every file the evaluation process executes against its manifest hash: the driver, the trainer modules, every engine file (as an exact set) and the secondary endpoints.
- The non-file entries the evaluation depends on: prompt, both engine-config digests, decoding, engine seed, evaluation and adapter pins, engine code hash, plus the trainer's registered values.

The bind file records the verified hashes. After export, the evaluate command validates its own archive with `verify_baseline`. If that fails, the record is renamed `*.INVALID` and the command raises. The gate, freeze and FinalTest notebook pass the manifest file through (`gate(..., manifest_path=...)`; `gate --manifest` on the CLI).

## B4 — writer ownership

**The lock.** `WRITER.lock` in the training root holds `session_id`, `host`, `pid`, `acquired_at`, `heartbeat_at` and `heartbeats`.
- It is created exclusively. A background thread refreshes the heartbeat every 30 s, and only while this session still owns the lock.
- `run_train` takes the lock before reading the plan and holds it until the outcome is logged.
- A second session is refused (exit 2, nothing logged). The refusal shows the holder and the age of its last heartbeat.
- A lock never expires by age.

**STARTED report.** `train_attempt` writes the STARTED `train_report.json` first, before verification and model loading.

**No automatic close.** `preflight` no longer reconciles. `next_run` and `reconcile()` refuse an open attempt unless `confirmed_no_other_session=True`.

**Recovery.** `recover_stale_writer(..., confirmed_no_other_session=True)` (CLI `--recover-stale-writer`) does three things in order:
1. Appends a timestamped record to `WRITER_RECOVERIES.jsonl`.
2. Closes each open attempt as `infrastructure`, with a `recovery` field and detail text in the finish event.
3. Releases the stale lock.

**Train notebook.** It has `RECOVER_STALE_WRITER = False`, plus a markdown note on stale writers. The control cell no longer calls `tp.reconcile`. It runs the recovery only when the flag is True, prints the lock state, and stops if a lock is held.

**Extra safeguard.** If a session finds it lost its lock during the attempt (another session recovered the root), it does not append its own finish. This keeps the log consistent.

**Your call:** a confirmed recovery keeps a numerical or protocol class if the attempt's own report on disk already records one. Otherwise it closes the attempt as infrastructure. I added this so a recovery can never turn a halting failure into a retry, but it is my refinement of the brief's "close as infrastructure". Please confirm or overrule.

**Limitation:** the exclusive create is atomic on one filesystem. Across two Colab VMs sharing Drive, the lock is cooperative, because Drive sync is eventual. That is why the heartbeat is shown to the operator and recovery needs explicit confirmation.
